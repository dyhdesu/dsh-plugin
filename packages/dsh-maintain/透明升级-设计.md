# dsh-maintain 双目录安装与链接升级设计

## 状态与目标

设计规格已经实施落地（A/B 双目录编排、候选验证、链接切换与升级锁，见
src/managed-*.mjs），本文记录设计口径与取舍；实施与本文的偏差以代码与
README 为准并回写本文。

**原全局包已有文件保持原样，仅新增dsh_link目录链接；两个包外新目录交替安装；
原dsh命令通过这个链接启动目标版本。**
目标是正常使用和常见失败下可靠，不承诺断电、强杀、外部并发npm或链接丢失时
强一致/自动恢复。链接丢失允许人工恢复已确认的原npm入口，再按外部npm节重装；
不保证同版install重建入口。这是用户接受的异常恢复边界。

本文替换原“三槽＋启动分发器”的设计，不保留其实施路径。
历史[候选树规格](<候选树升级-BDD.md>)、[审查](<候选树升级-审核.md>)及
[验收](<候选树升级-验收.md>)仅作参考，不继承其强一致不变量和G1—G5发布要求。
历史探针不证明本文A/B复用、命令重定向和profile绑定已经验证。

## 用户可见行为

- 初装仍为 `npm i -g @deepseek-ai/dsh`，启动仍为 `dsh web --no-open`。
- 原PowerShell/sh循环和第三方service启动命令不改，不增加dsh-managed命令，不改PATH。
- 插件首次升级会修改该安装的命令入口指向；不移动或改写原全局包已有文件，
  仅在包目录内新增一项dsh_link目录链接。
- 点击升级:后台准备目标,成功切链接后按确认窗勾选收尾("安装后自动重启宿主",单次意图默认开):
  勾选时正常结束DSH交第三方再次拉起;取消勾选则宿主继续运行当前版本,手动重启生效,重启前不能再次升级。
  没有拉起者或只配置on-failure时,正常退出不会自动重启,用户再执行原命令即可。
- 外部再次全局npm安装可能还原入口，这是允许的；插件不监视或自动抢回控制权。
- 支持目标为常规npm-global部署的Windows、Linux、macOS和Linux Docker。
  每个平台须真实测试；只读安装、npx缓存、源码checkout、Electron更新不在本期范围。

## 目录与依赖

从当前实际运行的安装发现原global prefix P，取真实路径，不从候选局部prefix误判。
管理根 `M=P/.dsh-maintain/` 位于原DSH包之外，每个prefix独立一份。
需要M、原包新增链接位置及命令入口可写，失败报权限错误，不自动sudo、不换prefix。
安装身份从实际CLI/宿主安装锚点的canonical路径识别，不从插件自身位置、NODE_PATH
或候选内npm config prefix猜测。A/B运行时核对记录的原prefix、原包与命令入口。
A/B只能是M内预定真实目录；发现目录自身为未知symlink/reparse point时停止清理安装。

```text
原npm全局安装/
  原DSH包/                   已有文件不移动、不修改、不删除
    dsh_link → M/install-a/node_modules/@deepseek-ai/dsh
  原命令入口 dsh             指向原包/dsh_link/<CLI>，名称与位置不变

M/
  install-a/                 完整局部npm安装及依赖
  install-b/                 完整局部npm安装及依赖
  state.json                 当前操作阶段、目标版本、运行路径与切换结果
  upgrade.lock               本插件正常请求互斥
  log/                       有界轮替日志及最近一次入口原文备份
```

A/B不是两个单独DSH包副本，每个都有完整npm依赖闭包。用精确版本在备用目录安装：

```text
npm install --prefix <备用目录> @deepseek-ai/dsh@<精确版本>
```

实际执行经已发现的npm CLI和argv数组，不接受任意shell命令模板。
候选安装隔离npm userconfig/cache，验证child强制设置独立DSH_HOME、HOME，Windows
同时设置USERPROFILE；不继承生产DSH_HOME。复制配置时外部数据根/绝对路径映射至
临时副本，不能映射或不能保证隔离则拒绝验证；不沿用指生产/旧global/A/B的宿主
fallback链接。开发工作副本junction可保留，但必须报告宿主依赖实际来自候选。
CLI名称与bin相对路径从manifest读取；一期要求bin.dsh与首次登记相对路径一致，
拒绝绝对/越界/变化的路径，核验文件与可执行权限。接入后仅切link，不偷偷换bin路径。
不只复制包目录，不把新依赖补进原global tree，不共享A/B的node_modules。

Node默认按真实模块路径解析依赖，但DSH的安装/profile双锚点、fallback链接及
工作副本junction均须实测。生产装载按宿主原生机制解析新树。本仓开发profile仍只经
dev-link管理，不手工补NODE_PATH/profile链接或编辑依赖行。

候选验证口径（用户决策收窄）：验证对象是候选包可用性，不是服务运行——
不拉起宿主服务、不复制生产配置/插件拓扑副本。已实施口径为依赖树完整性检查
（npm ls --omit=dev）+ 候选CLI真实执行冒烟（`node <候选bin> --version`，
隔离候选环境，自然退出），实现于 managed-upgrade.mjs validateCandidate，
与验收脚本同源。冒烟通过即证明模块图完整加载、peer 真实解析、顶层初始化不炸；
配置拓扑绑定验证明确不做。

## 命令入口重定向

创建dsh_link不会自动改变原dsh命令，需要首次重定向已发现的真实命令入口。
链接放原global包目录内，使npm入口的字面目标仍属于原包path；若直接指包外M，
已读npm bin-links会将它视为其它包入口并可能拒绝重装（EEXIST）。新增链接可以被
npm删掉，候选安装实体仍在包外M。这个布局必须纳入重装/卸载测试，不能只测启动。

| 平台 | 操作 |
|---|---|
| Windows | 原npm生成的ps1/cmd及存在的sh shim，保持Node选择、argv/stdin/exit码逻辑，只把DSH入口目标改至原包/dsh_link下的CLI |
| Linux/macOS | 原npm bin symlink改为指向原包/dsh_link下的CLI；不覆盖原包的真实bin文件，保留目标可执行权限 |

不新增常驻launcher，不复制CLI内容，不dynamic import候选，不替换整个global
node_modules。已有alias、未知自定义shim或多个冲突prefix不能自动修改，明确报布局错误。
Windows入口逐个写回并读回验证，保留此次原文；不是多文件原子操作，允许异常恢复需
手动npm重装。正常写失败尝试恢复此次已改入口，不因部分成功就报告接入完成。

Linux/macOS dsh_link为目录symlink，Windows优先本地junction。
POSIX用临时symlink＋rename替换；Windows允许移除旧junction再建新junction的短暂缺口，
不称原子。每次操作先核验路径是本插件预期的链接，不能把同名真实目录递归删除。
删除链接只删除链接本身，须有平台测试防止误删目标。切换失败尝试恢复旧目标，恢复
失败报告实际路径和npm重装方法，不先结束当前正常服务的DSH。

## 双目录重复升级规则

真实运行入口/安装路径以及dsh_link真实目标为主要依据；state只辅助诊断。
运行路径与链接不一致可能意味着切换未完成或外部npm重装，不凭state直接清目录。

| 运行来源 | 链接状态 | 正常下一步 |
|---|---|---|
| 原全局版 | 未接入 | 优先空闲A，验证后建链接并重定向命令入口 |
| A | 指向A | 清理并安装B，验证后切到B |
| B | 指向B | 清理并安装A，验证后切到A |
| 原全局版 | 全部命令入口已还原，旧链接可能仍留A/B | 核验两个目录没有活跃使用者；优先不被现有链接引用的目录，验证后重新接入 |
| 原全局版 | 命令入口已指A/B但当前宿主尚未退出 | 视为切换未完成，停止下一轮升级，不清理任一有引用目录 |
| A/B之一 | 链接缺失、指另一目录或入口已变 | 停止本轮升级，报告状态不一致；先结束旧宿主/重装或修复后重试 |

重复升级的必须规则：

1. 本插件每个prefix一次只有一个升级，锁记录owner/操作ID，重复请求返回忙或现有进度。
   不实现OS强互斥；只负责正常插件请求，不与外部npm形成事务。发现残留锁须核验owner，
   不能仅凭时间过期判断安全；异常核验不清取消操作，人工恢复。
2. 备用目录不能是当前实际运行目录、dsh_link目标或已知仍使用该目录的进程来源。
   使用已登记PID/启动身份和运行路径做正常检查；不能确认时不复用。
   一期前提为该安装单生产实例，无手动并发旧CLI/未知消费者。没有强进程树保证。
3. 仅清理本管理根中确认空闲的A/B目录；先确认前次npm/验证子进程已经结束。
   npm父进程退出不能当作所有lifecycle后代必然结束，异常中断后复用须额外核验。
   不对正在运行目录再npm，不建立第三个发行目录。
4. 每次清空备用目录后完整重装；候选失败不切链接，不自动覆盖失败目录重试。
   重试是核验空闲后新一轮清理安装。state写失败在切换前停止操作。
5. 新版启动后旧目录保留到下一次升级准备；下一轮会覆盖它，不保证永久回退历史。
   本方案只保留当前和暂时上一版，没有同时保留“上一版＋候选”的第三槽。
6. 原全局包仅一份固定存在；两目录反复复用，日志/入口备份有界替换，不永久保存
   每次升级目录和完整报告。生产DSH_HOME、profile、会话及数据从不位于待清目录。

目录路径会复用，普通文件加载不受generation保护；已明确接受这点，靠避免复用活跃
目录降低风险，不用新增代际账本假装解决。管理根与槽位必须由当前可信用户拥有且不可被不可信主体写入；Node路径API的递归清理不承诺抵御同UID并发恶意替换目录项。未知占用时取消比带风险清理更简单。

## 正常升级时序

1. 发现prefix、实际运行版本/目录、命令入口和链接，取得插件升级锁。
2. 固定目标精确版本；选择备用目录，核验空闲、磁盘空间和可写权限。
3. 清理备用目录，定向安装完整依赖，记录进度与npm输出。
4. 检查manifest精确版本与npm依赖树，并以 node 真实执行候选CLI（--version冒烟，
   自然退出，不起宿主服务）；验证失败结束操作。
5. 提示/遵守停机许可，暂停新工作，等待活跃任务结束；不能安全暂停则不切链接。
6. 若首次/外部npm还原后接入，先确保候选有效、链接可达，再更新命令入口。
   已接入时只切dsh_link。每步读回入口/链接和目标可读性；失败尽力恢复旧选择。
7. 记录“已切换，等待再次启动”，释放本轮锁，立即请求当前DSH正常结束。
   安装、验证、链接及入口写入全部在当前容器退出前完成。
8. 第三方再执行原dsh命令，新进程从链接目标加载完整新树。插件加载后对照操作ID、
   实际运行路径和版本记录“新版已运行”；只有页面/加载诊断正常才显示正常恢复。
   插件自身未加载时无法自动报告，UI不能仅以旧磁盘版本号推断升级成功。

记录状态不对外层启动构成gate；切换后进程因故未退出，不允许立即发起下一轮升级。
下一轮检测实际运行路径与链接不一致，返回明确错误。没有watchdog、一次启动许可、
自动kill或自动回滚，新版故障仍可能被外层循环反复拉起。这是当前取舍的一部分。

## 外部npm、Node及Docker

- 原global package已有文件不改，仅新增dsh_link。用户再次`npm i -g`/卸载按npm
  语义执行。命令入口可能重建或保留旧形式，不假定同版install一定触发重建；
  链接丢失后若重装仍保留接管入口，停止进程后按保存的原目标恢复npm入口，或仅
  移除已确认本插件接管的命令入口再重装；不得删除未知入口，不默默添加--force。
  下轮升级重新检查并接入；不支持与外部npm并发，不后台抢回控制权。
- npm显示的全局版本仍是原包版本，与A/B实际运行版本可以不同；UI必须显示实际运行
  版本和来源目录，不把npm ls -g当运行版本。外部npm明确回到其安装版本属于允许行为。
- npm uninstall不保证删除树外M，可留待显式清理；清理先停止相关进程，禁止递归跟随
  dsh_link删除原包或其它目录。清理不提供宿主必须正常才能执行的恢复承诺。
- nvm切Node/prefix视为另一安装；保持原npm命令行为，不跨prefix自动复用A/B。
  候选使用当前实际Node做验证，Node/ABI变化不能靠旧检查结果放行。
- Docker有内部循环与容器restart两种情况；正常exit0需第三方策略覆盖。
  on-failure不重拉时标等待用户再次启动，不伪报升级已运行。
- 同一容器restart通常保留入口和A/B；recreate可丢弃它们，允许回到镜像原安装。
  仅挂DSH_HOME不会保存入口/A/B，不能声称一定跨recreate保留升级。
  原global包不删也不等于破损入口自动fallback，必要时用npm重装恢复。

## 故障边界

| 故障 | 行为 |
|---|---|
| 下载/安装/候选验证失败 | 保留运行目录与现有入口/链接，输出失败阶段 |
| 备用目录忙、文件占用、权限不足 | 取消，不强删，不切链接 |
| 链接切换/入口重写普通错误 | 尝试恢复原目标/入口；失败保留诊断和重装说明 |
| state/日志损坏、owner核验不清 | 不据它选目录清理；停止升级，允许人工恢复 |
| 切换途中断电/强杀/链接丢失 | 不承诺自动恢复；允许npm重装重新获得原dsh入口 |
| 新版生产启动失败或插件不兼容 | 不自动回退/阻止外层重启；可人工恢复未被复用的旧安装或npm精确重装 |
| 新版已修改生产数据 | 代码回退不恢复数据；兼容性需用户确认，不自动拿旧代码读新状态 |

接受短暂链接缺口、多入口部分写入、旧进程通过可变路径晚加载等剩余风险。
不是概率成功率承诺；没有实测统计不写“99%”。正常路径可验收，已知异常明确报错。

## BDD验收场景

### 首次升级且原包不动

Given 标准npm全局安装，原入口指向原包，单实例运行；
When 插件安装并验证A，链接接入成功并正常结束；
Then 原包已有文件未改、唯一新增项为dsh_link，原dsh命令与参数不变，第三方下一轮从A启动。

### 连续升级与目录数量

Given 当前A运行且链接指向A，B无活跃消费者；
When 安装B并切换、重新启动，再准备下一轮升级；
Then 下一轮仅安装空闲A，连续十次仍只有A/B两个安装目录，没有第三槽/UUID目录堆积。

### 当前目录与旧进程保护

Given 备用目录有旧宿主或未结束安装进程，或运行路径与链接不一致；
When 请求升级；
Then 不清理它、不切链接，返回占用/不一致，不能按TTL放行。

### 候选失败与普通切换失败

Given 当前版本正常运行；
When 注入npm失败、依赖缺失、验证不通过或链接权限错误；
Then 安装失败不改入口/链接；切换失败尝试恢复且不得报告成功；运行目录未被安装改写。

### 参数、链接与真实依赖

Given Windows ps1/cmd/sh或POSIX bin symlink入口；
When 通过原dsh执行web、顶层version/help和app-help等原命令；
Then 参数/stdio/exit语义保持，Node main gate正常执行，目标依赖来自完整A/B闭包，
profile按宿主机制实际加载正确，不能仅验证CLI文件存在。

### 外部npm重装与再次接入

Given A/B已使用，用户停止进程并外部全局重装；
When 原dsh恢复全局入口后再次请求插件升级；
Then 不抢回旧入口，发现原prefix与运行路径，选空闲目录安装，验证后重新接入；
不会把全局npm版本与A/B运行版本混为一谈。若同版重装未重建入口，核验后保持实际
接入状态；丢失链接时先按记录恢复原npm入口再重试，不宣称同版install自动修复。

### Docker退出与异常恢复边界

Given 内部循环或覆盖正常退出的restart策略；
When 切换完成并正常exit；
Then 不依赖容器退出后worker，下一轮可运行新版本；on-failure＋exit0不报已运行。
When recreate或切换强杀导致链接/入口丢失；
Then 明确不保证自动恢复，按外部npm节恢复已确认的原入口并重装；同版install不
保证重建入口，测试不得伪称原子切换或裸重装必然恢复。

### 隔离验证与跨平台

Given 独立测试prefix/HOME/profile/cache/随机端口；
When 对Windows、Linux、macOS、Docker分别运行上述测试及echo链路；
Then 不触碰生产环境、不消耗真实LLM，清理仅本轮创建进程；未测平台标未验证。
